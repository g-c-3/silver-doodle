- [ ] **Phase 6 — Daily game-definition generation.** Server pieces built and sanity-tested (2026-09-14) — see below. Client (`attempt.js`) and `score-replay` not yet updated to consume this; both still run on Phase 4/5's client-generated-seed stub.
  - [x] **`server/functions/generate-daily-games/index.ts`.** Service-role, idempotent (no-ops if the date already has definitions). For a given IST calendar date (defaults to today; accepts a `gameDate` override for backfill), generates all 12 game definitions: a 0-25 theme shuffle per game (stored as the DB's 1-26 `theme_id`) and a fixed, deterministic 8x8 `board_pattern` per slot (seeded `${gameDate}:${gameIndex}:${slotIndex}:board`, same RNG/board-gen algorithm as `game-engine.js`/`score-replay`). Sanity-tested in Node: deterministic given the same seed, all 312 (12 games x 26 slots) generated boards confirmed playable and match-free at generation, all 12 theme shuffles confirmed as valid 26-length permutations.
  - [x] **`server/functions/start-attempt/index.ts`.** User-authenticated. Assigns a player's random 0-11 serving-order permutation on their first call of a given day (`player_daily_order`, validated by the existing Phase 2 `validate_game_order` trigger), works out which attempt-of-the-day a call represents, maps it through that permutation to a `game_index`, fetches the corresponding definition's 26 slots, inserts a new `attempts` row, and returns `{attemptId, gameDefinitionId, attemptNumberToday, slots[]}` to the client. This is also what resolves the Phase 5 persistence blocker — `attempts.game_definition_id` now has something real to point at.

Flagged clearly for the next device-adjacent session.

- [ ] **Phase 5 — Score integrity.** Edge Function built and sanity-tested (2026-09-14) — see below. Persistence to `attempts` deferred, not yet checked off as complete.
  - [x] **`server/functions/score-replay/index.ts`.** Accepts `{seed, levels[]}` (one record per finished/failed level — see docs/ARCHITECTURE.md Section 5 for the exact payload contract), deterministically re-derives every level's board from the seed, replays each submitted move through a 1:1 TypeScript port of `game-engine.js`'s match/cascade/scoring rules, and returns the authoritative score/time-bonus/lives-used/ad-lives-used/levels-reached. Rejects illegal moves, life-pool overclaims, ad-life-before-pool-exhausted, wrong move counts for a claimed-completed slot, and out-of-budget elapsed-time claims. Sanity-tested standalone against a Node-side comparison harness (board generation, swap/cascade scoring, and full-slot replay all verified byte-identical to `game-engine.js`'s own output) before delivery, not just reasoned about.
  - [x] **Client wiring.** `client/src/js/attempt.js` now assembles the `{seed, levels[]}` payload live during play (`pushLevelRecord()`) and submits it via `window.db.functions.invoke('score-replay', ...)` at attempt end (`submitAttempt()`), replacing the old console-only payload log. The attempt-summary screen shows a "(validating…)" preview of the client-computed figures until the Edge Function's response arrives, then switches to the server-authoritative numbers (or a "not validated" state if the call fails).
  - [ ] **Not yet done — persistence.** The function computes and returns a result but does not write to `public.attempts`. Phase 6's `start-attempt` function now resolves the original blocker (a real `game_definition_id` exists, via `daily_game_definitions`), but `score-replay` itself still isn't wired to UPDATE the `attempts` row `start-attempt` created — that wiring is Phase 7/8 territory, not attempted yet.
  - [ ] **Not yet done — deployment.** `deploy-functions.yml` (Phase 11) doesn't exist yet, so this function isn't actually live in the Supabase project — it's been sanity-tested locally (Node) only, not run against the Supabase Edge Runtime. Needs a manual deploy or Phase 11 to actually reach players.
  - [ ] **Known, deliberate trust boundary:** match/cascade scoring is fully replayed and never client-trusted. Per-level *elapsed time* (which drives time bonus) is still client-reported, bounded to that level's own fixed budget (60s/30s + 60s per life/ad-life actually used, both independently validated against the shared 3-life pool) — a modified client can shift a small time-bonus figure within its own level's budget but can't fabricate points, lives, or levels. See docs/DECISIONS.md.
