- [x] **Phase 6 — Daily game-definition generation.** Server pieces built (2026-09-14), and client + `score-replay` wiring completed same day — see below. Not yet deployed (Phase 11 / manual cron setup still open).
  - [x] **`server/functions/generate-daily-games/index.ts`.** Service-role, idempotent (no-ops if the date already has definitions). For a given IST calendar date (defaults to today; accepts a `gameDate` override for backfill), generates all 12 game definitions: a 0-25 theme shuffle per game (stored as the DB's 1-26 `theme_id`) and a fixed, deterministic 8x8 `board_pattern` per slot (seeded `${gameDate}:${gameIndex}:${slotIndex}:board`, same RNG/board-gen algorithm as `game-engine.js`/`score-replay`). Sanity-tested in Node: deterministic given the same seed, all 312 (12 games x 26 slots) generated boards confirmed playable and match-free at generation, all 12 theme shuffles confirmed as valid 26-length permutations.
  - [x] **`server/functions/start-attempt/index.ts`.** User-authenticated. Assigns a player's random 0-11 serving-order permutation on their first call of a given day (`player_daily_order`, validated by the existing Phase 2 `validate_game_order` trigger), works out which attempt-of-the-day a call represents, maps it through that permutation to a `game_index`, fetches the corresponding definition's 26 slots, inserts a new `attempts` row, and returns `{attemptId, gameDefinitionId, attemptNumberToday, slots[]}` to the client.
  - [x] **Client wiring.** `client/src/js/attempt.js`'s `startAttempt()` now calls `start-attempt` and stores the returned slots; regular-level boards come straight from `slots[slotIndex].boardPattern` (a defensive copy, since `beginLevel()` no longer generates them); themes come from `slots[slotIndex].themeIndex` instead of a client-side shuffle. Bonus-round boards (not pre-stored — no schema slot for them) are still generated client-side, but now seeded off the shared `gameDefinitionId` instead of a per-player seed, so they're identical for every player who reaches that bonus point in the same daily game.
  - [x] **`score-replay` wiring.** `server/functions/score-replay/index.ts` now fetches the attempt's `game_definition_id` from the `attempts` row itself (not the request body, so a tampered client can't point replay at an easier game) and the stored 26 `board_pattern` rows from `daily_game_definition_slots`, and uses those directly instead of regenerating boards from a seed. Bonus boards are re-derived server-side with the exact same `gameDefinitionId`-seeded formula the client uses. Sanity-tested in Node: a simulated client play-through (stored board + the new `:refill`-keyed rng) validated correctly, a bonus-level replay validated correctly, and a deliberately mismatched board was correctly rejected.
  - [x] **Persistence — closes the Phase 5 gap.** `score-replay` now UPDATEs the `attempts` row on a valid replay (`status`, `completed_at`, `score`, `time_bonus_micros`, `lives_used`, `levels_reached`, and a same-day `score_day` placeholder — real Section 8 score_day edge cases are still Phase 8). A write failure after a successful replay is surfaced distinctly (`persisted: false`) rather than as a validation failure, since the computed result is still correct.

Along the way: fixed all three functions to read the project's actual `SUPABASE_SECRET_KEYS`/`SUPABASE_PUBLISHABLE_KEYS` (this project uses the new key system, not legacy `service_role`/`anon`), re-granted `service_role`'s table privileges (were missing on `daily_game_definitions` for an undiagnosed reason), and added proper CORS handling (`OPTIONS` preflight + `Access-Control-Allow-*` on every response) that was missing from all three from the start. See docs/DECISIONS.md's 2026-09-14 "deployment debugging" entry.

  - [ ] **Newly found gap (2026-09-14, during the device playthrough, not a Phase 5/6 design flaw):** an in-progress attempt has no persistence on the client side at all — if the browser tab gets reloaded (mobile browsers do this routinely when a backgrounded tab is reclaimed for memory), the app just boots back to the home screen with no memory of the attempt, and that attempt's `attempts` row is left permanently `status: 'in_progress'` in the database — orphaned, never scored, never cleaned up. Not attempted as a fix here since it's a client-side resume/recovery feature, not a Phase 5/6 scope item — needs its own design (resume from `localStorage`/IndexedDB on reload? detect and let the player abandon a stale in-progress attempt on next `start-attempt` call?) before it's picked up.
- [x] **Phase 5 — Score integrity.** Edge Function built (2026-09-14); persistence and client/board wiring completed same day via the Phase 6 session — see above and below.
  - [x] **`server/functions/score-replay/index.ts`.** Accepts `{attemptId, levels[]}` (one record per finished/failed level — see docs/ARCHITECTURE.md Section 5 for the exact payload contract), deterministically re-derives every level's board (Phase 6: from stored data, not a client seed), replays each submitted move through a 1:1 TypeScript port of `game-engine.js`'s match/cascade/scoring rules, and returns the authoritative score/time-bonus/lives-used/ad-lives-used/levels-reached — and persists it (see Phase 6's persistence bullet above). Rejects illegal moves, life-pool overclaims, ad-life-before-pool-exhausted, wrong move counts for a claimed-completed slot, out-of-budget elapsed-time claims, and (Phase 6) a mismatched/tampered board. Sanity-tested standalone against a Node-side comparison harness before delivery, not just reasoned about.
  - [x] **Client wiring.** `client/src/js/attempt.js` assembles the `{attemptId, gameDefinitionId, levels[]}` payload live during play (`pushLevelRecord()`) and submits it via `window.db.functions.invoke('score-replay', ...)` at attempt end (`submitAttempt()`). The attempt-summary screen shows a "(validating…)" preview of the client-computed figures until the Edge Function's response arrives, then switches to the server-authoritative numbers (or a "not validated" state if the call fails).
