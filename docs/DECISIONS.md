# Decisions

ADR-style log, most recent at bottom of each dated block. Written in impersonal third person; no attribution to individuals.

## 2026-09-11 — Seed session

**Monetization model.** The cash-prize mechanic (daily ₹1,000 Amazon Pay gift card) was removed entirely. The game is free-to-play with no monetary prize of any kind. Consequence: the original plan's legal/compliance apparatus for India's online-gaming law (PROGA classification, 30% TDS on winnings, prize-claim KYC) no longer applies, since no stake or prize exists on either side of play. Ad revenue is retained purely as a standalone revenue line, not as a cost-offset against a prize.

**Leaderboard scopes.** Daily, weekly, and all-time leaderboards were added (previously daily-only). All three scopes use the identical 7-tier ranking cascade (see ARCHITECTURE.md Section 7), evaluated over a widening attempt pool per scope, rather than introducing a separate aggregation rule per scope — this reuses one cascade implementation across all three UI surfaces, including the per-player "how you got this rank" breakdown.

**Attempt attribution across midnight.** An attempt is scored against the calendar day it *completes* on, not the day it started, so that each day's leaderboard is guaranteed final and immutable once its settlement job runs — no late-arriving score ever needs to be reconciled into an already-closed day. Slot-cap enforcement (12/day) is kept independent, keyed to the attempt's *start* timestamp instead, so a player can never gain an extra start by timing it near midnight. This intentionally allows, at most once per player per day boundary, an attempt whose score lands on the following day without having consumed one of that day's slots.

**Attempts per day.** Increased from 3 to 12.

**Level structure.** A free level-selection UI (player picks which of 26 alphabet-labeled levels to play, tile greys out on completion) was proposed, then reversed in favor of retaining forced-sequential play. In the final design, slot position (A–Z) is fixed and always carries the same move target; which of the 26 themes is shuffled into each slot varies per game definition (see ARCHITECTURE.md Section 4). This preserves the original difficulty ramp (tied to sequence position, not theme identity) while still introducing daily variety and anti-scouting protection.

**Board & theme fairness model.** Scaled from 3 fixed boards/day (one per the old 3 attempts/day) to 12 fixed game definitions/day — identical board pattern + theme shuffle for every player, with only the per-player *serving order* of the 12 randomized. This is a direct scale-up of the original "identical boards, skill decides rank" design, not a new mechanic.

**Ad cadence.** Both the ad-life grant and bonus-round entry gate were reduced from 2 required rewarded-video ads to 1 each. This also simplifies the server-side state machine (one atomic ad-completion event per trigger, rather than tracking partial "1 of 2 watched" state), at the cost of roughly halving the plan's earlier per-run ad-volume placeholder — revenue projections were rebuilt against a worst-case 3-ads/attempt figure (2 ad-lives + 1 bonus-round ad by level 4) rather than the old flat estimate.

**Auth.** Switched from phone-number verification to email + OTP only, via Supabase Auth. Only name and email are collected at signup — no phone, no birthdate, no address. Name and email are editable later; email changes require OTP re-verification.

**Age gate.** Removed. Left as an open item: without an age gate or birthdate field, the product does not collect data that would give it "actual knowledge" of a minor user under India's DPDP Act, which reduces (but does not eliminate) exposure under DPDP's children's-data provisions. Flagged for legal review before any wider launch, not resolved here.

**Weekly reset.** Weekly leaderboard resets Monday 00:00 IST. All-time leaderboard never resets.

**All-time stats & calendar.** Added a per-player all-time stats view (days played, total attempts, best/least day) and a month/year calendar with dot-marked played days drilling into per-day attempt detail. Best/least day defined by highest/lowest single-attempt score that day — deliberately the same metric as leaderboard tier 1, to avoid a second, inconsistent definition of "performance" on the profile page.

**Backend platform.** Supabase (Postgres + Auth + Edge Functions) selected over Firebase. Primary reason: the 7-tier leaderboard cascade is a native multi-column `ORDER BY` query in Postgres, versus requiring hand-rolled denormalized aggregate fields updated transactionally in Firestore. Secondary reasons: Supabase's free tier bundles auth, database, and serverless functions without needing to wire together separate vendors (e.g. Neon + a third-party auth provider); Edge Functions (Deno/TypeScript) serve the same server-authoritative validation role Cloud Functions would have.

**Analytics split.** Firebase Analytics (linked to AdMob for revenue-by-cohort reporting) and Crashlytics are retained as a narrow, deliberate exception to the "backend is Supabase" rule — no Firestore, no Firebase Auth, to avoid duplicating auth/database logic across two vendors.

**Client/engine.** Capacitor selected over Unity and Godot. Reasoning specific to the development process: Unity and Godot scenes are authored visually in a GUI editor and cannot be reliably hand-written and verified as text without running the editor to preview them. HTML/CSS/JS can be authored and verified as plain text. The existing playable browser prototype's match/cascade/scoring logic is reused directly rather than rewritten in GDScript or C#. Trade-off accepted: WebView-rendered animations are less inherently smooth than a native game engine's — judged an acceptable cost for a grid-based tile-swap game with no physics.

**Score integrity model.** The client sends `{seed, moves[]}`, never a raw score. A single Supabase Edge Function call per completed attempt deterministically replays the run and computes the authoritative score server-side. This is a batched (one call per attempt), not per-level, validation design — chosen specifically because it reduces Edge Function invocation volume roughly 8x (from ~96 to ~12 calls/player/day at 12 attempts/day), which directly extends the free-tier DAU ceiling.

**Infrastructure cost planning.** Modeled the Supabase free tier as holding up to roughly 900 DAU before the database-storage quota (500 MB, the tighter of the two free-tier constraints) is exceeded — tighter than the ~1,400 DAU ceiling implied by the Edge Function invocation quota alone. Per-attempt/per-day summary rows are treated as permanent data (required indefinitely by the all-time-stats and calendar features) and are to be kept as compact as possible; any deeper move-by-move replay/audit logging beyond those summary rows is to carry a short retention window rather than living in Postgres indefinitely, since only the summary rows are actually needed forever.

**Repo & distribution.** Single public monorepo (`g-c-3/silver-doodle`) holding client, server, docs, and CI workflows together. Manual APK sideload via GitHub Releases during development; Google Play submission deferred to a later phase, gated on the privacy policy page (served via GitHub Pages) and production AdMob ad unit IDs being in place.

**File delivery workflow.** Files are never pushed directly to the repository by an automated integration; every created or modified file is delivered as a complete, ready-to-download file and uploaded to the repository manually. This matches the existing project-instructions convention rather than introducing a new one.

**Project name.** Working name changed from "Emoji Puzzle" to "Match Emojis Daily." The prior name was found to already be in use by an existing, well-established Play Store app during a naming-conflict search, prompting the change. "Match Emojis Daily" returned no exact-title collision in the same search pass, though the broader "emoji + match" naming space remains crowded with similarly-named apps; the name was kept anyway for its clarity and for explicitly signaling the daily-reset competitive structure, which is a genuine product differentiator. Renaming was low-cost at this point since the prior name existed only in `README.md` and `privacy-policy.html`, not in the repo name, package ID, or any shipped code.

**Project name (second change).** Working name changed again, from "Match Emojis Daily" to "Emoji Daily Rush." No exact-title collision was found for "Emoji Daily Rush" either. Flagged and accepted risk: "Emoji Rush" (the two-word core of this name) is itself an existing, established title used by two unrelated existing games, a closer partial collision than "Match Emojis Daily" had with anything found. Chosen anyway. Same low renaming cost applies as the prior change.

**Project name (final).** After evaluating one further candidate, "Match Emoji : Rush Hour" — rejected on discovering "Rush Hour" is itself a well-known, decades-old trademarked puzzle game (plus an unrelated film franchise), a stronger collision than either prior candidate — the working name reverted to "Match Emojis Daily." Deciding factors across all candidates considered: "Match Emojis Daily" had the lowest collision risk of any option checked, and unlike every "Rush"-based variant, it does not set a genre expectation (fast-paced/reflex) that mismatches the actual game (a 60-second-per-level, skill-and-consistency-scored daily puzzle with a 7-tier leaderboard cascade). This is treated as the final name barring a specific reason to revisit it.

**Theme art.** All 26 themes use native Unicode emoji glyphs for piece art — no custom-drawn or licensed art assets, no art-production pipeline. This removes the previously open "per-theme piece-set art still needs finalizing" item entirely.

**Theme list redefinition.** The original 26-theme list was replaced with a new list chosen specifically for native-emoji availability, resolving the constraint noted above at the prior session. Dinosaurs (only 2 distinct native emoji) was merged into a new Reptiles & Amphibians theme, which retains a dinosaur glyph. Butterflies & moths (effectively 1 distinct glyph) and Gemstones & crystals (effectively 2) were dropped in favor of richer categories. The original generic "emojis" (smiley-face) theme was kept, renamed Faces & Emotions, replacing a redundant near-duplicate of Wild Animals (Safari & Jungle) that had been drafted during this redefinition. The final 26 themes each carry exactly 6 native emoji, and all 156 glyphs across the full set are unique with zero repeats — resolving the cross-theme-uniqueness requirement (bonus levels mix glyphs from the 3 most recently completed themes, so any two themes can end up adjacent under the daily shuffle). Final theme list and piece sets are recorded in ARCHITECTURE.md Section 3.1.

## 2026-09-12 — Phase 1 infra session

**Package name.** Decided: `com.gc.matchemojisdaily`.

**Android keystore password model corrected.** ROADMAP.md originally assumed four independent secret values for Android signing (keystore password, key alias, key password, plus the keystore file itself). In practice, `keytool`'s modern default output format (PKCS12) does not support separate store and key passwords — the tool silently ignores a second password value if one is supplied. The actual model is one password used for both `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_PASSWORD` GitHub secrets, alongside the alias and base64-encoded keystore file. Corrected in ROADMAP.md and noted here so future sessions don't reintroduce the wrong assumption.

**Supabase access token exposure and rotation.** A Supabase personal access token was pasted directly into the chat during setup, despite guidance not to. The token was treated as compromised regardless of whether it had actually been misused, revoked immediately, and regenerated with the same scoped permissions (Edge Functions: Read-write only, limited to this project) before being added directly as the `SUPABASE_ACCESS_TOKEN` GitHub secret without passing through chat a second time. Recorded here as the standing practice going forward: genuine secrets (access tokens, API secret keys, signing passwords) are never to be pasted into the conversation, even by request or for reference-saving purposes — they go directly into GitHub secrets or are generated and delivered as files, the same way the Android keystore credentials were handled. Non-secret identifiers meant to be embedded in client code or a shipped APK (AdMob App ID and ad unit IDs, Supabase project URL and anon key, Firebase config values) are not subject to this restriction.

**Firebase Crashlytics enablement deferred.** Crashlytics has no meaningful console-only setup step before the Crashlytics SDK is integrated into real app code — it presents as a "get started" flow requiring the SDK, not a toggle. Enablement is deferred to Phase 4, when the SDK dependency is actually added to the generated Android project, rather than attempted prematurely against a project with no app code yet.

**Supabase custom SMTP still deferred.** Confirmed as an intentional gap, not an oversight: the built-in Supabase email sender is sufficient for development/single-tester use and remains rate-limited and unsuitable for real signups. Revisit before Phase 12 (or sooner if testing needs exceed the built-in sender's rate limit).

## 2026-09-12 — Phase 3 auth session (link-flow pivot)

**Typed OTP code dropped in favor of a tap-the-link flow.** ARCHITECTURE.md Section 10 specifies "email + OTP," which was first implemented as a typed 6-digit code (`verifyOtp`). Manual testing surfaced a free-tier constraint: Supabase's default email sender does not allow editing email template content — required to inject the `{{ .Token }}` placeholder the code screen depends on — without either upgrading to Supabase Pro or configuring a custom Send Email hook or custom SMTP, both of which are deliberately deferred (see the 2026-09-12 Phase 1 infra block above). Rather than standing up either of those early, the auth flow was switched to use Supabase's default confirmation-link email as-is: the player taps the link, is redirected back to the app's Site URL with a session already established, and no template customization is needed. This still satisfies "email + OTP" in spirit (a link is itself a one-time-use token), just not as a typed code. Revisit if a typed-code UX is specifically wanted later — that would now require the same custom SMTP / Send Email hook step this pivot avoided.

**Site URL / Redirect URLs now a required manual config item.** Supabase Dashboard > Authentication > URL Configuration must have Site URL and an allow-listed Redirect URL set to the GitHub Pages app URL (`https://g-c-3.github.io/silver-doodle/client/src/index.html`), or Supabase refuses to redirect back after a confirmation link is tapped. `client/src/js/config.js` carries the same URL as `SITE_URL` and must be kept in sync with the dashboard value if the app's hosting location ever changes.

## 2026-09-12 — Phase 2 database schema session

**`daily_game_definitions` split into two tables.** ARCHITECTURE.md Section 6's indicative column list (`date, slot_index, board_pattern, theme_id, move_target`) conflated two different granularities — "12 rows/day, one per game definition" versus per-slot columns that only make sense at 26-rows-per-definition granularity. Resolved as two tables: `daily_game_definitions` (12 rows/day, one per game index 0–11) and `daily_game_definition_slots` (26 child rows per definition, one per slot A–Z, holding `theme_id` and `board_pattern`). `move_target` was dropped from stored data entirely — it's a fixed function of `slot_index` per Section 3.1's table and is kept as a shared constant in client and Edge Function code, not duplicated as per-row data.

**Leaderboard cascade averaging tiers — attempts_started vs. attempts_completed.** ARCHITECTURE.md Section 7's tiers 2/4/5/7 average a metric "across attempts actually played," while tier 6 counts "number of attempts played" with fewer ranking higher. These two phrases needed separate interpretations to be implementable: tiers 2/4/5/7 (which average score, time bonus, lives used, and levels played) are computed over *completed* attempts only, since a forfeited attempt has no meaningful score/time-bonus/levels value to fold into an average. Tier 6 counts every attempt *started*, completed or forfeited, since a forfeited attempt still consumed one of the 12 daily slots and a false "fewer attempts, same result" advantage shouldn't be obtainable by forfeiting cheaply. The stats tables (`daily_stats`, `weekly_stats`, `all_time_stats`) accordingly track `attempts_started` and `attempts_completed` as two separate counters rather than one. Flagged for confirmation before Phase 7 (leaderboard queries) is built on top of it.

**Score-integrity payload is never persisted.** The raw `{seed, moves[]}` replay payload submitted per attempt is not stored in the `attempts` table or anywhere else in this migration — only the server-computed summary (score, time bonus, lives used, levels reached, status) is kept, and permanently, per the existing infra cost-planning decision that only summary rows need to live in Postgres indefinitely. If move-by-move audit logging is wanted later for dispute investigation, it should live in a separate table with an explicit short retention window, not `attempts`.

**RLS posture: service-role-only writes everywhere except `users.display_name`.** Every table has RLS enabled. Players can `SELECT` their own private rows (`attempts`, `player_daily_order`, `user_year_activity`) and `SELECT` public aggregate/reference data (`daily_stats`/`weekly_stats`/`all_time_stats`, `daily_game_definitions`/slots, and a name-only `leaderboard_profiles` view over `users`). No client-side `INSERT`/`UPDATE`/`DELETE` policy exists on any table except `users`, where only `display_name` is effectively editable (an update trigger reverts `id`/`email` changes from non-service-role callers). This directly enforces the score-integrity rule at the database layer, not just in application code: even a modified/rooted client cannot write a fabricated attempt or score, because the client's Postgres role has no INSERT grant on `attempts` at all — only the score-replay Edge Function's service-role connection can.

## 2026-09-12 — Phase 2 fix (missing grants + linter hardening)

**Missing table GRANTs — confirmed bug, not a style choice.** The original Phase 2 migration enabled RLS and wrote policies on every table but never ran a `GRANT` statement for the `authenticated` role. RLS only filters rows once a role already has baseline table access; without the GRANT, every client read failed with "permission denied for table X" before RLS was even evaluated. This surfaced immediately when Phase 3 auth testing tried to read `public.users` right after a successful sign-in. Fixed in `supabase/migrations/20260912010000_phase2_fix_grants_and_hardening.sql` with explicit `GRANT SELECT`/`UPDATE` statements per table for `authenticated`. Any future new table needs an explicit grant added at creation time — it will silently permission-deny otherwise, RLS policies notwithstanding.

**`leaderboard_profiles` SECURITY DEFINER view kept as-is, against the linter's recommendation.** Supabase's Security Advisor flags the view as critical for running with the view owner's permissions rather than the querying user's. That's intentional here: the view's whole purpose is to expose `id` + `display_name` for *every* player (for the leaderboard), while the underlying `users` table's RLS restricts direct access to "your own row only." Switching to `security_invoker = true` (the linter's suggested fix) would make the view inherit that same restriction, so every player would only ever see their own name through it — silently breaking the leaderboard rather than improving security. Since the view exposes only two non-sensitive columns and nothing else from `users`, the SECURITY DEFINER behavior is the correct choice, not an oversight. Left un-"fixed" on purpose; don't let a future linter pass "helpfully" flip this.

**Other linter findings from the same pass, fixed as safe/uncontroversial:** `search_path` explicitly set to `''` on three trigger functions that were missing it (`set_updated_at`, `protect_users_identity_columns`, `validate_game_order`) to close a search-path-hijacking vector; the default `PUBLIC EXECUTE` grant revoked from `handle_auth_user_sync()` since it's only ever meant to fire as a trigger, never called directly (confirmed this doesn't break the trigger — trigger execution runs under the function owner's context regardless of the invoking session's EXECUTE grants); and `auth.uid()` rewritten as `(select auth.uid())` in the five RLS policies that referenced it directly, a query-planner performance fix with no behavior change. The "Leaked Password Protection Disabled" finding was left alone as not applicable — this app has no password auth at all (OTP/link only).

## 2026-09-12 — Phase 4 rebuild against the uploaded prototype

The prior "Phase 4 core game client session" block (above) was written before the actual prototype file (`daily-match-playable-demo.html`, a 4-level playable proof-of-concept of the full 26-slot design) was made available — that session flagged the prototype as missing from the repo and proceeded on invented defaults instead. The file was uploaded immediately after and turned out to specify several mechanics the invented version got wrong. This block supersedes the relevant parts of the prior one; the values that turned out to already be correct (8x8 board, 6 piece types, 3 starting lives) are not repeated here.

**Life pool extends the current level's timer; it does not regenerate the board.** The invented first pass had a life loss reset the level (fresh board, moves budget restarted). The actual prototype instead adds 60 seconds to the same level's clock and continues on the same board with moves/score progress intact. Corrected to match — this is a materially different (and more player-friendly) design than what shipped first.

**The 3 regular lives are consumed automatically, in order, with no player choice, before the ad-earned life is ever offered.** The invented first pass presented a choice ("use a pool life or watch an ad") on every timeout. The prototype only offers the ad-life choice once all 3 regular lives are already spent. Corrected to match.

**Running out of every life ends the whole attempt immediately, not just the current level.** The invented first pass treated "out of lives" as ending the attempt at the current `levels_reached` — that part was actually already correct in effect, but the pathway to it (per-level retry loop) was wrong; there is no retry loop in the real design, only the timer extension described above, then attempt failure.

**Every level is preceded by a mandatory theme-reveal screen.** Not present in the invented first pass at all — the prototype always shows theme name, piece emoji, and level requirements before starting the timer, non-skippable for regular slots, skippable for bonus rounds. Added as `screen-level-reveal`.

**Bonus round specifics, previously guessed at, now confirmed:** 30-second timer (not 60), no move cap at all (timer-only), no life risk on timeout, and the tile mix is deterministic — 2 emoji drawn from each of the 3 most recently completed slot themes (not a random 6-of-18 draw as the invented first pass did).

**Ad count reconciled against the standing ad-cadence decision, not copied from the prototype.** The uploaded prototype simulates 2 sequential rewarded ads per bonus-round entry and per ad-life grant, and its own header comment says as much. This directly contradicts the 2026-09-11 "Ad cadence" decision already on record in this file, which reduced both gates from 2 ads to 1 specifically to simplify the server-side state machine and to rebuild revenue projections around a lower per-attempt ad-volume figure. The prototype is judged to predate that decision rather than to supersede it — nothing in this session's context suggests the ad-cadence reduction was reversed. Both dev-stub ad gates in `client/src/js/attempt.js` grant on a single simulated ad, per the existing decision, not two.

**One place the prototype's actual code is treated as a bug, not copied.** The prototype's own on-screen copy for a failed level states "an incomplete level banks zero score and zero time bonus," which matches ARCHITECTURE.md Section 3.3 exactly ("An incomplete level contributes 0 to both Score and Time Bonus") — but the prototype's code never rolls back `state.score`, which is incremented in real time as matches are made during play. In the prototype, if a level fails partway through, whatever score had already accrued from matches made during that level silently survives despite the on-screen claim otherwise. This implementation holds each level's score in a scratch total (`levelScore`) that is only added to the attempt's running total on that level's successful completion, so a failed level genuinely contributes 0, matching the written spec rather than the prototype's actual (undocumented, likely unintentional) behavior. Time bonus was already only banked on success in both versions, so no change was needed there.

**Time-bonus display format adopted from the prototype.** ARCHITECTURE.md Section 3.3 specifies a "sec:milli:micro" digit-clock accumulation but not a display format. The prototype's `mm:ss:ms:µs` zero-padded format is adopted as-is for the attempt-summary screen.

**Life/ad-life extension duration.** Fixed at 60 seconds (same as a full regular level's timer), per the prototype — not previously specified anywhere.

## 2026-09-13 — Visual/interaction pass against screenshots

A round of feedback against screenshots of the live Phase 4 build, gathered one screenshot at a time and applied in one pass at the end per explicit request. Grouped by what changed:

**Confirmed bug: the reveal screen's Skip button showed on regular levels.** `styles.css` only ever defined `.screen.hidden` and `.error.hidden` — scoped rules, not a general one. Toggling a plain `hidden` class on the reveal screen's Skip button (or, as it turned out, on the toast bar added this session) did nothing, because no CSS rule matched a bare `.hidden` on those element types. Fixed with a single generic `.hidden { display: none !important; }` rule; the two scoped rules were left in place as harmless redundant duplicates rather than risk touching something else that depends on their specificity.

**Board centering and responsive sizing.** The board was only horizontally constrained (`max-width` + `margin: 0 auto`) and `#screen-game` overrode the base `.screen` rule's `align-items: center` with `flex-start`, which is what pushed everything to the top with dead space below. Removing that override lets the base `.screen` flex-centering handle both axes for the whole HUD+board block as a single unit — no bespoke centering logic needed, since it already existed and was just being opted out of. The board's own size is now `min(94vw, 56dvh, 460px)` (both a viewport-width and viewport-height bound, whichever is smaller) so it shrinks on short or narrow screens instead of overflowing, rather than a fixed max-width that assumed a tall enough viewport.

**Six piece types, six border colors, consistent across every theme.** Colors are keyed to the board's own piece index (0–5), not to which emoji happens to occupy that index in the current theme — so the mapping is stable across all 26 themes and the bonus round's mixed set. Selecting a tile now plays a pulsating glow in that tile's own color (a CSS `--tile-color` custom property plus one shared keyframe animation, rather than one keyframe per color) instead of the previous static border-and-inset-shadow highlight.

**Swipe added alongside tap-tap, not replacing it.** Both gestures are live: a short pointer down/up on one tile is treated as a tap (the original select-then-tap-adjacent flow); a longer pointer movement (≥18px) before release is treated as a swipe and swaps directly with whichever adjacent tile the drag pointed toward. Implemented with `pointerdown`/`pointerup` rather than separate mouse/touch handlers, which covers touchscreens and desktop testing alike without duplicated code. The `pointerup` listener is registered once on `document`, not per-cell — an earlier draft attached it per-cell and would have left a stale in-progress drag if the pointer was released outside any tile (e.g. dragged off the board edge), corrupting the next touch's interpretation. Caught in review, not from a live report.

**Match/invalid feedback.** `GameEngine` gained `trySwapDetailed`, which exposes the pre-clear swapped board and the exact set of cells cleared by the swap's own immediate match (not just the final post-cascade board and a total score, which is all the original `trySwap` returns). This lets the UI show the swap happen, then blast exactly those tiles in their own color roughly 90ms later, then settle into the fully-resolved board after cascades roughly 420ms after that — real animation timing rather than an instant board replacement. Scoping note: only the swap's own first-round match is animated at exact positions; further cascade rounds resolve directly to the final board without their own individual blast animation, since animating those exactly would require re-deriving tile identity across gravity shifts between rounds, which wasn't judged worth the added engine complexity for an 8x8 board. An invalid swap/swipe now shakes both tiles and, where the Vibration API is available (Android Chrome/WebView, which covers this app's actual target — not iOS Safari), triggers a short vibration.

**Life-loss and ad-life feedback.** Hearts now render as filled (❤️) for lives remaining and explicitly emptied (🤍) for lives already used, rather than the previous version, which just shortened the repeated-heart string and gave no visual sense that something had been "spent." Each life/ad-life event now shows a 3-second auto-dismissing toast in a small bar at the bottom of the board, with copy that says what happened and what it bought ("+60s on the clock, same board") rather than a generic label.

**Live countdown shows running ms/µs, not just whole seconds.** Reformatted to `ss:mmm:µµµ`, ticking every 50ms instead of every 100ms so the display reads as continuously running. This is a cosmetic consistency choice with the existing sec:milli:micro time-bonus format — it is not a claim that the countdown is accurate to real microseconds, and the code comment says so, so a future session doesn't mistake it for a precision requirement.

**HUD redesigned as chip cards plus a score strip.** Replaced the single-row flex list of five plain text spans with a 4-up grid of small labeled cards (Level / Timer / Moves / Lives) and a separate score strip below showing the running score and, new, the live running time-bonus total (previously only shown at attempt-summary) — both because a live-updating running total reads better in a strip of its own, and because it makes the summary screen's final number less of a surprise.

**Level/bonus-round completion is now its own screen, not an instant jump.** Previously `finishRegularLevel`/`finishBonusLevel` moved straight to the next reveal or bonus prompt with no acknowledgment of what just happened. Added `screen-level-complete`: a ~1.5s CSS-only confetti burst (colored spans animated outward and faded, using the same 6 tile colors, generated and cleaned up in JS — no image assets) plus a small stat grid (points this level, time bonus banked, cumulative score, lives status) and a continue button whose label and destination are decided by the calling function (`Play next`, `Continue` for a bonus round, or `See results` on the final slot) and stored as a one-shot callback rather than a hardcoded next screen, so the same screen serves both regular and bonus completions without a branch in the router.

**Bonus-round prompt given a deliberately more "special" visual treatment and copy.** Was a plain emoji + gray paragraph + button, indistinguishable in weight from a routine confirmation dialog. Given a pulsing radial-glow badge, a two-color headline ("Free points, zero risk"), and copy that leads with what the player gets rather than a neutral mechanical description of the trigger, per feedback that it read as low-stakes/plain when it's meant to be a rewarded moment.

**Theme-aware accent coloring.** Each theme gets a distinct accent hue via `hsl((themeId * 360 / 26), 72%, 64%)` — spread evenly around the color wheel rather than 26 hand-picked colors, which costs nothing to keep correct if the theme count ever changes and guarantees even, visibly distinct spacing without hand-tuning. Applied as a single `--theme-accent` custom property on the document root (simpler than scoping it per-screen, and harmless since the only rules that reference it are the reveal ticket, the live score number, and the level-complete screen — the attempt-summary screen doesn't use it, so a stale value from the last-played level lingering into summary has no visible effect). Bonus rounds get a fixed gold accent instead of a theme hue, since they mix 3 themes and no single hue would represent that. This is deliberately kept independent of the per-tile-type border colors above, which stay fixed regardless of theme — the two systems answering different questions (which piece is this vs. which level am I in) shouldn't share a palette or they'd become impossible to tell apart at a glance.

**Confirmed bug: the attempt summary's "lives used" figure excluded the ad-earned life.** It only ever read `livesUsedInRun` (the 3-life pool), never `adLifeUsedThisLevel`/whether an ad-life had been granted at all during the attempt. Added `a.adLivesUsedInRun`, incremented wherever the ad-life is actually granted, and a shared `livesStatusText()` helper (used by both the level-complete screen and the summary) that reads e.g. "3/3 regular + 1 ad-life" instead of just "3/3."

## 2026-09-14 (continued further) — deployment debugging: new API key system, missing grants, and CORS

Live deployment (walking through it interactively with the person, not a coding session in the usual sense) surfaced three real issues none of Node-side sanity testing could have caught, since all three are specific to the actual Supabase project's configuration rather than the function logic itself. Recorded here because each one changes something about how these functions must be written going forward, not just how this one project happened to be configured.

**The project uses Supabase's new `sb_publishable_.../sb_secret_...` key system, not the legacy `anon`/`service_role` JWT keys.** All three functions originally read `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')`/`SUPABASE_ANON_KEY`, which are the *legacy* auto-injected secrets and are not guaranteed populated on a project provisioned under the new key system. Switched all three to `SUPABASE_SECRET_KEYS`/`SUPABASE_PUBLISHABLE_KEYS` (JSON-dictionary env vars, read via `JSON.parse(...)['default']`), which Supabase's current docs confirm are unconditionally provided regardless of which key system a project uses. Any future Edge Function in this repo should source keys this way from the start, not the legacy var names.

**`service_role` (the Postgres role, not the API key) was missing table-level grants on `daily_game_definitions`.** Surfaced as `permission denied for table daily_game_definitions` on `generate-daily-games`'s first real insert attempt — a genuine Postgres GRANT gap, not an RLS policy rejection (RLS failures read differently) and not the key-sourcing issue above (that was already fixed and confirmed live at the point this error appeared). Root cause not fully diagnosed — Supabase normally grants `service_role` full access to every `public` schema table by default — but resolved by explicitly re-running `grant all privileges on all tables/sequences in schema public to service_role` plus `alter default privileges ... grant all on tables to service_role`, confirmed via `information_schema.role_table_grants`. Flagged in case it recurs on a future table: this is a one-line SQL fix, not a design problem.

**None of the three functions handled CORS.** The client runs on a `github.io` origin calling `*.supabase.co` — cross-origin, so browsers send an `OPTIONS` preflight before the real `POST`. All three functions only ever checked `if (req.method !== 'POST') return 405`, which rejected the preflight itself. Found via the Invocations log showing `405 OPTIONS` entries alongside the real request, not via local reproduction (Node sanity testing has no browser CORS model at all, so this class of bug is structurally invisible to that kind of test — a live invocation log was necessary). Fixed by adding an `OPTIONS` short-circuit returning `200` plus `Access-Control-Allow-*` headers, and adding those same headers to every response (error responses too — a CORS-missing error response is just as invisible to the calling browser as a CORS-missing success response). This should be treated as a standard part of the Edge Function boilerplate for this project going forward, alongside the key-sourcing pattern above — any new function needs both from the start, not discovered by way of a live 401/405 during testing.

## 2026-09-14 (continued) — Phase 5/6 wiring: client, score-replay, and persistence closed in one pass

Same day, immediately following the Phase 6 server-pieces session — the "next session start point" it left was picked up directly rather than waiting for a new session boundary.

**`score-replay` now trusts the `attempts` row for `game_definition_id`, never the request body.** The client still sends `gameDefinitionId` in its payload (useful for logging/debugging), but the server ignores it in favor of reading `game_definition_id` straight off the `attempts` row looked up by `attemptId` — after verifying that row's `user_id` matches the authenticated caller. This closes a tampering vector that a naive "just trust whatever gameDefinitionId the client sends" implementation would have left open: a modified client could otherwise claim to have played an easier daily game than the one it was actually assigned.

**Bonus-round boards stay un-stored and client/server-derived, by design — not a gap being carried forward accidentally.** Revisited this from the earlier same-day Phase 6 entry now that it's actually being wired end to end: confirmed the reasoning still holds. Since `gameDefinitionId` is a shared, server-assigned value (identical for every player playing that `game_index` that day), seeding both the client's bonus-board generation and `score-replay`'s bonus-board validation off the exact same `${gameDefinitionId}:bonus:${slotIndex}:board` key guarantees every player sees an identical bonus board at that point, with no database storage needed at all. Extending the Phase 2 schema with a bonus-board table was considered and rejected for this session — it would touch already-shipped schema for a case that's already fair without it.

**Regular-slot refill randomness uses a distinct `:refill`-suffixed key, separate from the `:board` key that produced the stored starting layout.** Before Phase 6, one rng stream served double duty: generating the initial board, then continuing to drive cascade refills after every match, in client and `score-replay` alike. Now that regular-slot starting boards are pre-stored data (no generation call consumes any rng), reusing the old `:board`-suffixed key for refills would work but reads as accidental key reuse rather than a deliberate choice. Introduced `:refill` as its own explicit suffix (`${gameDefinitionId}:slot:${slotIndex}:refill`) in both `attempt.js` and `score-replay/index.ts` — cosmetic for correctness (either key would produce a valid, matching result on both sides, since it's the same formula in both places) but clearer to read and to reason about six months from now.

**`score-replay` writes to `attempts` on success, closing the Phase 5 persistence gap flagged earlier the same day.** A write failure *after* a successful, correct replay is surfaced as `{...result, persisted: false, persistError}` rather than folded into the `valid: false` failure path — the computed score is genuinely correct at that point; only the database write didn't land. Treating that as a validation failure would be misleading (it isn't a cheat-detection outcome) and would need its own reconciliation path regardless, which is real Phase 7/8 scope, not invented here.

**`score_day` is set to "today" (IST) as a placeholder, not a real Section 8 implementation.** Section 8's score_day attribution rules (e.g. how an attempt spanning midnight, or a late-arriving submission, should be attributed) haven't been designed yet. Using today's date is the obviously-correct behavior for the overwhelming majority of attempts (started and finished well within one calendar day) and avoids leaving the column NULL, but is explicitly not meant to be the final word on the edge cases — flagged in both the code comment and here so it isn't mistaken for a considered decision when Phase 8 actually addresses it.

## 2026-09-14 — Phase 6 daily game-definition generation

**Theme storage uses a 1-26 convention in the database, 0-25 everywhere else — conversion happens only at the two Edge Function boundaries.** `daily_game_definition_slots.theme_id` already carried a `check (theme_id between 1 and 26)` constraint from the Phase 2 schema, while the client's `THEMES` array and every piece of game logic index 0-25. Rather than relaxing the DB constraint to match the code (which would've meant touching already-shipped, green Phase 2 SQL for a cosmetic reason), the conversion is confined to `generate-daily-games/index.ts` (0-25 internal shuffle -> `+1` on insert) and `start-attempt/index.ts` (`theme_id - 1` on the way out as `themeIndex`). Nothing else in the codebase needs to know this conversion exists.

**Board patterns are stored as fully-materialized jsonb grids, not just a seed string.** The original architecture sketch left it ambiguous whether "board pattern" meant a stored seed (regenerate on demand) or a stored grid. Went with a stored 8x8 grid of piece indices: it's what actually satisfies "identical board for every player" without relying on every consumer (client, `score-replay`, any future admin/debug tooling) independently re-running the exact same board-gen algorithm bit-for-bit forever. The generation algorithm is still seeded and deterministic (`${gameDate}:${gameIndex}:${slotIndex}:board`) so the stored grid is itself reproducible/auditable, but nothing downstream needs to regenerate it — they just read the row.

**`generate-daily-games` is idempotent by design, not by accident.** A cron misfire, a manual retry after an unclear error, or an operator manually re-running it to check on a day are all realistic scenarios given this ships to a solo-maintained project with no on-call rotation. Checking for existing rows before writing anything, and no-op'ing cleanly rather than erroring or double-inserting, means none of those scenarios can corrupt a day already served to players. The cost is a small "did I actually mean today, or should I check first" burden on manual backfill use (the `gameDate` override param) — considered worth it.

**`start-attempt`'s per-player order assignment is seeded, not `crypto.getRandomValues`-random.** Seeded off `${gameDate}:${user.id}:order` so a retried/duplicate call from the same player on the same day can't race into two different orders being computed (only one gets inserted, but the retry logic re-reads rather than trusting its own possibly-different computation). This is safe specifically because serving *order* carries no fairness or security stakes between players — every player still eventually plays all 12 identical game definitions that day; only the sequence differs, and there's no scenario where a player benefiting from knowing or influencing their own order changes their outcome, since the 12 games themselves are fixed and identical regardless of order.

**Session scope deliberately stopped at "server can hand out and generate definitions" — client/score-replay wiring left for next session.** `attempt.js` still generates its own seed client-side and `score-replay/index.ts` still regenerates boards from that seed rather than consuming a stored `board_pattern`. Wiring both in the same session as building the generation/serving infrastructure was considered and rejected: it would touch four files (two new, two substantially modified) in one pass with no natural checkpoint, versus a clean split where this session's two new server functions can be sanity-tested and reviewed on their own before the client starts depending on them.

## 2026-09-14 — Phase 5 score-replay Edge Function

**Payload restructured from a flat `moves[]` log to per-level records.** ARCHITECTURE.md Section 5's original phrasing, `{seed, moves[]}`, was written before the shape of a "move" was pinned down. The Phase 4 client's actual move log (`{slot, from, to, tMs}`, with `tMs` computed as `levelSeconds*1000 - msRemaining()`) turned out to be ambiguous for replay: `tMs` resets toward zero every time a life extends the timer (since it's computed against a fixed `levelSeconds` constant, not a cumulative clock), and the log carried no explicit record of *when* a life or ad-life was actually used, or which level a run of moves belonged to once the shared life pool and slot index had moved on. Restructured as `{seed, levels: [{slot, isBonus, moves: [[r1,c1,r2,c2],...], livesUsedThisLevel, adLifeUsed, elapsedMsAtEnd, outcome}]}` — one record per finished-or-failed level, pushed at the moment that level's outcome is decided (`pushLevelRecord()`), so there's no reconstruction-after-the-fact ambiguity. `elapsedMsAtEnd` is now a cumulative value across any life extensions on that level (tracked via `levelElapsedBaseMs`/`currentSegmentMs`), not a per-segment-relative one. This is a payload-format decision, not a mechanics change — nothing about lives, timing, or scoring rules themselves changed.

**Time-bonus timing remains a client-reported, budget-bounded value — a deliberate, documented trust boundary, not an oversight.** The score-integrity rule requires the client never send a raw *score*, and this holds: every point is recomputed server-side by replaying the submitted moves through the same match/cascade logic as `game-engine.js`, with illegal moves rejected outright. But *time bonus* depends on real elapsed wall-clock time during play, and the batched single-call-per-attempt design (chosen specifically to cut Edge Function invocation volume ~8x, per the 2026-09-11 "Score integrity model" entry) means there's no per-move server round-trip to measure that time independently. The Edge Function instead bounds each level's `elapsedMsAtEnd` to that level's own fixed time budget (60s or 30s, plus exactly 60s per life/ad-life actually used — both cross-checked against the shared 3-life pool and the "ad-life only after the pool is spent" rule). Net effect: a modified client could shift a small time-bonus figure within one level's own budget, but cannot fabricate points, extra lives, extra levels, or an inflated move count — the things that actually determine leaderboard rank via tiers 1-4 and 6-7. Revisit only if time-bonus gaming is later observed to matter enough to justify a per-move heartbeat design; not attempted here as a preemptive fix for a problem not yet shown to exist.

**Persistence to `public.attempts` deliberately deferred, not built this session.** `attempts.game_definition_id` is a `not null` foreign key into `daily_game_definitions`, which Phase 6 (daily game-definition generation) is what actually populates — that table has zero rows until Phase 6 ships. Writing to `attempts` now would require either a placeholder/fake `game_definition_id` (contradicting the whole point of that FK) or skipping the constraint (weakening a deliberate data-integrity guarantee from Phase 2). The Edge Function this session computes and returns the authoritative result but performs no database writes at all — a pure, side-effect-free validation step. Slot-cap enforcement (Phase 8) and score_day attribution (Section 8) are likewise out of scope until Phase 6/7 supply the pieces they depend on.

**Engine logic ported to TypeScript by hand, not shared via a build step.** Supabase Edge Functions (Deno) deploy each function's directory in isolation with no bundler step configured, so `server/functions/score-replay/index.ts` re-implements `game-engine.js`'s seeded RNG, board generation, match detection, scoring, cascade resolution, and swap validation as a direct 1:1 port rather than importing the client file. Verified for behavioral parity before delivery via a standalone Node comparison harness (not shipped, sandbox-only): identical board generation for a given seed key, identical scores and final boards across a sequence of swaps, and a full slot-A replay (9 moves, one life used) producing the exact expected time-bonus figure. Flagged as a standing maintenance risk: if `game-engine.js`'s match/scoring rules ever change, `score-replay/index.ts` must be updated to match by hand, or client-displayed and server-validated scores will silently diverge.

## 2026-09-15 (continued) — Idle-hint highlight corrected to show the resulting match, not the swap pair

## 2026-09-15 (Phase 8 start) — Slot cap made atomic; Phase 7 checked off

**Phase 7 marked done in ROADMAP.md** — backend (stats writes + cascade) and client screen both built and verified against live data this session (multi-player cascade confirmed correct with a second test account).

**12/day slot-cap enforcement replaced with an atomic Postgres function.** The prior version (`start-attempt/index.ts`) counted today's attempts, then separately inserted a new one — its own code comments already flagged this as a "soft guard, not the real Phase 8 cap" because nothing prevented two concurrent calls (a double-tap, a client retry racing the original request) from both reading the same count, both passing the `< 12` check, and both inserting. `start_attempt_slot` (new migration: `supabase/migrations/20260915000000_phase8_atomic_slot_cap.sql`) folds the count, cap check, `game_index` resolution, and the `attempts` insert into one `plpgsql` function under `pg_advisory_xact_lock(user_id, game_date)`, so a second concurrent caller's count always reflects the first caller's already-committed insert. ## 2026-09-15 (Phase 8 continued) — Heartbeat/timeout forfeit detection built

Closes the orphaned-in-progress-attempt gap logged in the 2026-09-14 session (a reloaded tab mid-attempt left the `attempts` row stuck at `in_progress` forever, with no resume/recovery and no way for it to ever settle).

**Two new pieces, split by responsibility rather than one function doing both:** `attempt-heartbeat` (client-invoked, `server/functions/attempt-heartbeat/index.ts`) only bumps a new `attempts.last_heartbeat_at` column (migration: `20260915010000_phase8_heartbeat_column.sql`) — it never marks anything forfeited. `forfeit-stale-attempts` (`server/functions/forfeit-stale-attempts/index.ts`) is a **scheduled** function, never called by the client, that sweeps for `in_progress` attempts whose heartbeat is more than 5 minutes stale and marks them `forfeited`. Splitting these keeps the trust boundary clean: the client can prove it's still there, but only the server's own clock (via the scheduled sweep) ever decides an attempt has gone stale — there's no path where a client request of any kind causes a forfeit.

**5-minute timeout vs. a 20s heartbeat interval** is deliberately generous (~15x) — this only needs to catch a genuinely abandoned session (app closed, force-killed, tab reloaded), not a missed beat or two from normal phone/network flakiness (backgrounding, a dropped request). A tighter window would risk forfeiting an attempt someone is still actively playing.

**A forfeited attempt scores 0 across the board and doesn't touch `record_attempt_completion`** — consistent with Score Integrity (the server never received move data for it to replay) and with the leaderboard's existing accounting model (Section 7 tier 6): it already incremented `attempts_started` when `start-attempt` ran, so a forfeit correctly shows up as "an attempt that didn't pan out" rather than silently vanishing from the count.

**`attempt-heartbeat` reads the row's current status before deciding what to report**, rather than inferring "forfeited" from an `UPDATE ... WHERE status = 'in_progress'` matching zero rows — that zero-row case is ambiguous (could mean *forfeited*, or could just mean the player's own `submitAttempt()` already completed it normally moments earlier), and reporting the wrong one would show a "this attempt was forfeited" alert to someone who just legitimately finished.

**Not yet deployed** — needs, in order: (1) run `20260915010000_phase8_heartbeat_column.sql` in the SQL Editor, (2) create `attempt-heartbeat` and `forfeit-stale-attempts` as new Edge Functions in the dashboard (and commit both to GitHub), (3) set up a Cron schedule for `forfeit-stale-attempts` (Supabase Dashboard → Cron, every 5 minutes — same mechanism as `generate-daily-games`'s existing 00:05 IST schedule, just far more frequent), (4) redeploy `client/src/js/attempt.js` (static file, no dashboard step needed). None of this has been exercised against live data yet.

**Remaining Phase 8 work:** attempt-history UI (start time, status, scored-day) — not started, separate client screen work.

## 2026-09-15 (Phase 8 continued once more) — Tab-switch was silently abandoning in-progress games

Root cause for two symptoms reported together: switching browser tabs mid-game force-navigated to Home (closing the game), and the next game started afterward showed an oddly-high score on its very first move.

**The actual bug:** `app.js`'s `onAuthStateChange` listener called `routeAfterAuth()` — which unconditionally navigates to `screen-home` (or `screen-name-setup`) — on every `SIGNED_IN` event. supabase-js re-fires `SIGNED_IN` with the *same* session whenever the tab regains focus/visibility (documented supabase-js behavior, not something this app does deliberately) — so every tab-switch-and-back silently ran the same navigation logic as a fresh login, yanking the player out of `screen-game` without ever calling `failAttempt()` or `finishAttempt()`. Since stopping the Phase 8 heartbeat and the level countdown timer only happens inside those two functions, the abandoned attempt's intervals kept running in the background, now pointed at whatever the module-level `a` in `attempt.js` got reassigned to on the *next* `startAttempt()` call (JS closures capture the variable, not a snapshot) — explaining the odd first-move score as most likely stale-timer interference rather than an actual score copy (a fresh attempt object with `totalScore: 0` is genuinely created every `startAttempt()` call; there's no code path that copies a score value across attempts).

**Fix:** a `hasRoutedOnce` flag restricts the actual `routeAfterAuth()` navigation to the first `SIGNED_IN`/`INITIAL_SESSION` event of a given page load. Later re-fires (tab-focus re-validation, not a new login) still update `state.session` so API calls keep using a fresh token, but no longer force navigation. This should also make the Phase 8 heartbeat/tick-timer cleanup work as originally designed, since the game session is no longer being silently killed out from under it by something unrelated to actually finishing or failing an attempt.

**Not fully verified yet** — this fixes the mechanism that was causing both symptoms, but hasn't been confirmed against a real repeat of the tab-switch scenario.

## 2026-09-17 — Phase 11 debugged to green; native app hardening; app icon

**`SUPABASE_PROJECT_REF` is a plain literal in `deploy-functions.yml`, not routed through a secret.** The first live run showed it resolving to an empty string despite `SUPABASE_ACCESS_TOKEN` being present — most likely added as a repo Variable rather than a Secret. Rather than chasing which GitHub Settings tab it needed to live under, the fix was to notice the project ref was never actually sensitive to begin with (it's already a plain value in `supabase/config.toml`'s `project_id` and written out in ARCHITECTURE.md Section 12) and stop treating it as one. General principle worth keeping: not everything that's *configuration* needs to be a *secret* — routing a non-sensitive value through secrets storage only adds a failure mode (wrong tab, typo'd name, never set) with no actual security benefit.

**Magic-link sign-in from inside the native app: custom URL scheme, not Android App Links.** The "correct," most-native-feeling fix for "the emailed link should open the app" is Android App Links — a verified HTTPS association that makes the *same* `https://` link open the app directly, no custom scheme needed. It was deliberately not used here: verification requires hosting `.well-known/assetlinks.json` at the domain **root** (`https://g-c-3.github.io/.well-known/assetlinks.json`), which is controlled by a different, separate GitHub Pages repo (the account's `g-c-3.github.io` user site) that this project has no established access to or even confirmed existence of — Android App Links verification is per-domain, not per-path, so hosting it under `silver-doodle`'s own project-pages path doesn't work. A custom `matchemojisdaily://auth-callback` scheme was used instead — self-contained entirely within this repo, no cross-repo dependency. Revisit App Links if/when there's a confirmed way to publish to that domain's root.

The deeper reason this isn't just a UX nicety: `signInWithOtp()` uses Supabase's PKCE flow by default, which stores a `code_verifier` in whichever origin actually made the request. The emailed link always opens in the system browser — a different origin than the app's own Capacitor WebView — so if sign-in was started inside the app, the code exchange genuinely cannot succeed in that browser tab; the matching verifier simply isn't there. Routing the callback back into the app isn't optional polish, it's required for the flow to complete at all when sign-in started in-app.

**Browsers require a genuine user gesture to hand off to a custom URL scheme; a JS-triggered redirect doesn't count.** First implementation used `location.replace()` fired automatically from an inline script the instant the callback page loaded — this got stuck on a blank page in live testing. This is a deliberate anti-abuse browser restriction (otherwise any page could silently launch arbitrary apps), not a bug in the redirect logic itself, and no amount of tweaking the JS would have fixed it. The working version replaces the automatic redirect with a real, visible, tappable "Open Match Emojis Daily" `<a href="matchemojisdaily://...">` button — a genuine tap satisfies the gesture requirement. **Do not reintroduce an automatic redirect here for the sake of a smoother-looking flow** — it will silently fail the same way again.

**Android edge-to-edge / status bar: Capacitor's Android WebView doesn't populate the standard `env(safe-area-inset-*)`.** `targetSdk` 36 (Capacitor 8.5.2's default) makes edge-to-edge mandatory on Android 15+, so content draws behind the system status bar by default unless explicitly padded for it. The natural fix — CSS `env(safe-area-inset-top)`, the standard web-platform mechanism — does not work correctly in Capacitor's Android WebView; confirmed via research rather than assumed, since shipping the wrong variable name would have looked correct in review and silently done nothing on-device. Capacitor 8's own Android core instead injects `--safe-area-inset-top/right/bottom/left` as custom CSS properties. **Any future safe-area CSS in this project must use `var(--safe-area-inset-*, 0px)`, never `env(safe-area-inset-*)`.** Applied to `.screen`'s base padding, plus `#screen-game` and `#screen-info` (each has its own padding override that fully resets the base rule, needing the same fix independently) and `.icon-btn-corner` (the corner-pinned logout/info buttons — `position: absolute` measures from the parent's padding edge and ignores padding entirely, so the screen-level fix doesn't reach it; needed its own `top` offset).

**App icon: "Option B" (three-tile diagonal match) with a neon green glow border, approved 2026-09-17.** Four SVG concepts were presented for approval before any code was touched, deliberately built from the app's own existing identity (dark background, the pink→purple gradient already used throughout, the puzzle-piece emoji already serving as the in-app logo) rather than a fresh brand exercise. This was surfaced explicitly — a rendered simulation of the circular crop was shown, not just described — and accepted as a known, deliberate tradeoff rather than something to silently fix or hide. Anyone revisiting the icon later should not "fix" this clipping without checking first; it was a conscious call, not an oversight (also stated directly in `client/assets/icon.svg`'s own header comment, so it survives even if this doc isn't read).

## 2026-09-18 — Phase 10 (Ads)

**Ad-watched verification is a real server-to-server SSV callback, not a client-invoked confirmation step.** The alternative considered — the client calling a new Edge Function itself right after the AdMob SDK reports a reward — was rejected outright: that's exactly the "client-reported ad watched flag" the standing score-integrity rule explicitly says never to trust, since a modified client could call that Edge Function without ever having shown an ad at all. Google's own SSV mechanism (AdMob's servers call the developer's backend directly, out-of-band from the device) is the only version of this that's actually server-authoritative — the whole reason it exists is to give backends exactly this guarantee.

**`ad_verifications` is a new table, not new columns on `attempts`.** An attempt can have at most one ad-life grant per level and one bonus-round entry per bonus slot, but there's no natural fixed-width column set for "which slots had a verified ad" — a slot-indexed jsonb blob was considered and rejected in favor of a proper child table, consistent with how `daily_game_definition_slots` already models a similar one-parent-many-children relationship rather than a wide/jsonb parent row.

**`ad_verifications` has no client-facing RLS policy in either direction — not even SELECT.** Every other table added since Phase 2 that reaches this point has at least a read-your-own-rows policy; this one doesn't, because nothing in the client actually needs to read it back — the local "ad watched" UI state (unlocking the life/bonus prompt) lives entirely in `attempt.js`'s in-memory attempt object for the duration of that one ad request, and is discarded either way once the attempt is submitted. Revisit only if a future feature (e.g. "ads watched this attempt" shown in attempt history) needs to read it.

**Google's `transaction_id` is the real replay-prevention key, not a composite of attempt/slot/type.** A second genuine ad watched for the same attempt+slot+type (e.g. the player backs out and re-triggers the same prompt) is harmless and doesn't need blocking — score-replay only ever checks *whether at least one* verified row exists for that key, so a second row is simply redundant, not a problem. `transaction_id UNIQUE` exists purely so a duplicate SSV callback (Google is documented to retry a callback that doesn't get a prompt response) can't be inserted twice, using AdMob's own already-unique identifier rather than inventing a second one.

**SSV signature verification implemented directly from Google's documented algorithm, not tested against a real callback.** This sandbox has no way to generate a genuine Google-signed SSV ping (that requires a real AdMob-served rewarded ad actually completing, which needs a live device/app). `admob-ssv/index.ts` was written to match the documented spec exactly (ECDSA P-256/SHA-256 over the raw query-string substring preceding `signature=`, verified against Google's published rotating key set at `gstatic.com/admob/reward/verifier-keys.json`) and the surrounding HTTP/DB plumbing was exercised for shape, but the actual cryptographic check itself is unverified. AdMob's console has a built-in "Send test callback" button on the ad unit's Server-side verification screen specifically for this gap — flagged as the concrete next-session verification step rather than something to guess is fine.

**`showRewardVideoAd()`'s promise never rejects on an early dismissal — caught by reading the plugin's native source before writing against it, not from a live bug report.** `@capacitor-community/admob`'s Android implementation (`RewardedAdCallbackAndListeners.kt`) only ever resolves that call's underlying `PluginCall` from the reward-earned callback; there's no corresponding `call.reject()` anywhere in the dismiss path. A naive `await AdMob.showRewardVideoAd()` would therefore hang forever if a player opened a rewarded ad and closed it before finishing. `attempt.js`'s `playRewardedAd()` instead races the plugin's own promise against a `Promise` that rejects the moment the `onRewardedVideoAdDismissed` or `onRewardedVideoAdFailedToShow` event fires, with a `settled` guard ensuring the reward path (which fires its resolve first, ahead of the dismiss event, per the SDK's own lifecycle) always wins when both could theoretically apply.

**AdMob App ID is a plain literal in the CI patch script, not a GitHub secret.** Same reasoning as `SUPABASE_PROJECT_REF` (see the 2026-09-17 entry) — it's already public in docs/ARCHITECTURE.md Section 12 and gets compiled directly into the shipped APK's manifest either way, so routing it through secrets storage would add a failure mode with no actual confidentiality benefit.

**AdMob App ID meta-data patched into `AndroidManifest.xml` by extending the existing `patch_android_manifest.py`, not a new script.** Considered a separate script (one concern per file) and rejected: both patches touch the same generated file in the same CI step, and the workflow already has exactly one step for "patch the manifest" — adding a second script would mean either running two near-identical steps back to back or restructuring the workflow step for no real benefit, versus one script with two clearly-separated, independently-tripwired patches. Verified in a sandbox against a real `npx cap add android` output (Capacitor 8.5.2, matching the pinned version) before delivery — both patches applied correctly to the real generated file, not just reasoned about against the previously-seen shape.

**Current AdMob ad unit IDs continue to be used as-is for this phase, not swapped for Google's official test unit IDs.** Consistent with the Phase 1 decision already on record (ROADMAP.md: "current IDs are usable for development") — revisiting that call wasn't in scope for wiring the rewarded-ad flow itself, and Phase 12 is where production identity work happens regardless.
